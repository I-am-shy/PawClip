### 已确定的技术决策

- **技术栈定为 Tauri v2 + Rust + SQLite**。选型主因：常驻后台进程对内存敏感，Tauri 30–60 MB vs Electron 150–300 MB。备选 Electron（快速验证）与 SwiftUI（仅 macOS）。
- 剪贴板捕获必须自己封装 `NSPasteboard`（`objc2` + `objc2-app-kit`），**不用 `arboard`**——它不暴露 `changeCount`，无法做变更检测。
- 中文搜索方案：FTS5 **`tokenize='trigram'`**，因为默认 `unicode61` 分词器对中文整段成词、子串搜不到。trigram 要求查询词 ≥3 字符，**两字词必须用 `LIKE '%xx%'` 兜底**，否则中文用户会认为搜索坏了。
- 去重：SHA-256 指纹 + 偏唯一索引 `uq_items_fp_alive ON items(fingerprint) WHERE deleted_at IS NULL`，重复复制只置顶+累加计数，不新增行。
- 过期三级优先级：`item.expires_at` > `category.ttl_seconds` > 全局默认 > NULL(永久)；`pinned=1` 强制不过期。计算值连同 `ttl_source` 一起落库以便 UI 解释原因。
- 过期采用**软删除进回收站保留 7 天**再物理删除 + 清理 blob，不直接物理删（历史数据误删代价过高）。

### v2 方案的关键结论

- Tauri 的**空闲内存瓶颈是 WebView（60–90 MB）而非 Rust 内核（8–12 MB）**。因此定下核心策略：**面板窗口闲置超时即销毁**（默认 300s），而非仅隐藏；Windows 额外叠加 WebView2 `TrySuspendAsync`。这是达成 15–30 MB 空闲内存的唯一有效手段。
- Rust 侧建议**不上 async runtime**，4 条 `std::thread` + `mpsc` 足够，省 ~1.5 MB 与启动时间。
- Windows **不需要轮询**：`AddClipboardFormatListener` + message-only 窗口（`HWND_MESSAGE`，独立线程跑消息泵）是事件驱动的，空闲 CPU ≈ 0%。macOS 只能轮询。
- 自写入守卫统一为**指纹比对**（`SelfWriteGuard`），不用 changeCount —— Windows 上拿不到自身写入对应的序号。
- Windows 独有坑：`OpenClipboard` 会因全局互斥返回 `ERROR_ACCESS_DENIED` 需重试；`CF_DIBV5` 必须手转 PNG（行按 4 字节对齐）；`"HTML Format"` 带 `StartHTML` 头部必须剥离；UIPI 会静默吞掉对管理员进程的 `SendInput`；面板需 `WS_EX_NOACTIVATE`。
- 备份包定名 `.clipbak`，**ZIP 容器**（不用 tar.zst，为了用户可双击查看 + 可验证性优先）。清单**最后写入**（流式导出时 stats 才知道）。缩略图不导出（派生数据）、文件类条目默认只存路径不内嵌。
- 导入必须**按分类名匹配而非 ID**、重映射所有引用、每 500 条 COMMIT、带 `import_id` 支持一键回滚。
- 安全面：ZIP Slip 防护的关键是 **blob 落盘路径由 sha256 重新计算，条目名不参与目标路径构造**。

### Go 可行性结论（附录 A）

**Go 完全可行。** 关键事实：

- macOS 需 **cgo + 约 150 行 Objective-C 桥**（`.m` 暴露 C 接口）。免 cgo 的 `purego` 方案冗长易错，不推荐。
- Windows **完全不需要 cgo**：`golang.org/x/sys/windows` + `syscall.NewCallback` 即可，比 Rust 的 `windows` crate 更省事。
- **不要用 `golang.design/x/clipboard`** —— 和 Rust 的 `arboard` 同一个毛病：不暴露 `changeCount`（变更检测必需）、不暴露原始 pasteboard types（判断 `org.nspasteboard.ConcealedType` 必需）。两语言都必须自写平台层。
- 数据库选 `mattn/go-sqlite3`（cgo），**FTS5 需加 `sqlite_fts5` 构建标签**。`modernc.org/sqlite` 纯 Go 但会再加 8–10 MB，不划算。

**代价的关键洞察（重要）**：用户最在意的"包量小"必须区分两个维度——

| 维度 | Go 相对 Rust 的增量 |
|---|---|
| **下载体积**（DMG/NSIS 压缩后） | **仅 +1–3 MB** |
| 安装后磁盘占用 | +5–8 MB |
| 空闲内存 | +2–6 MB |

即：**Rust/Go 的体积差会被压缩吃掉一部分，下载体积差距远小于直觉。** 而达成 15–30 MB 空闲内存的决定性因素是"系统 WebView + 面板窗口闲置销毁"，**与后端语言无关**。

→ 因此选型应基于**开发速度与语言熟悉度**，而非体积；建议：Go 熟 → Go+Wails v2；都不熟靠 AI 写 → Rust+Tauri v2（参考资料更多，如 EcoPaste）。

### 新增优化清单（DESIGN.md §15）

按收益排序，重点几条：
- **IPC 绝不传图片**（必须走 `asset://` / 静态资源，base64 塞 IPC 会卡 1 秒+）；搜索防抖 120ms + 取消上次查询
- 分页用 **keyset 而非 OFFSET**；合批提交（50ms 或 20 条）
- **WAL 定期 `checkpoint(TRUNCATE)`**，否则涨到几百 MB
- 启动时**不要每次 integrity_check**，改用 `clean_shutdown` 标记文件
- 列表查询**只取 preview 不取 text_content**
- **轮询热路径绝不分配**（macOS 只读一个 NSInteger）
- **验证"销毁"是真的**：销毁窗口后 log 实际 RSS，确认 WebView 子进程退出
- macOS 产物**必须带 ad-hoc 签名**，否则 Apple Silicon 内核拒绝执行
- 超大文本截断存储但**保留完整内容指纹**，否则去重会漏

### 剩余问题（仅 2 项）

1. **React 还是 Vue**（必须二选一）
2. **Go 还是 Rust 作后端**

**坑二：灰度阈值 / 洪泛填充抠背景必然失败**。方块外是一圈柔和环境阴影（左上 250–252，右下低至 212），而方块填充是 244–250 —— **阴影比填充更暗，灰度区间重叠**：
- 全局阈值 → 右下深色阴影被误判为方块内部
- 从四角洪泛填充 → 四角灰度本身 251/250/248/241 达不到阈值，**背景占比实测 0.00%**，一个像素都填不出去

→ 唯一可靠手段：**按几何形状生成圆角矩形遮罩**。

**坑三：遮罩半径必须 ≥ 源图实际半径**。源图圆角比同半径正圆略紧（45° 方向靠内 3–4px）。半径偏小则四角漏背景 / 阴影（右下漏的是深色阴影，深色桌面上很刺眼）。取 19%（实测 17.6% + 1.4% 余量）。验收图 `dist/preview-mask-check.png`：叠品红底做四角放大，任何品红穿透即失败。

### 🔴 阻塞项：Wails v2 无法做免抢焦点面板（→ DESIGN.md §0.1）

**已核对 Wails v2 官方 `options` 文档**：`mac.Options` 只有 `TitleBar` / `Appearance` / `WebviewIsTransparent` / `WindowIsTranslucent` / `ContentProtection` / `About` —— **没有任何窗口类控制**；`windows.Options` 也**没有 `WS_EX_NOACTIVATE`**。

问题核心：macOS 要同时"窗口能成为 key（接收搜索输入）"和"不激活本 App"，只有 `NSPanel` + `NSWindowStyleMaskNonactivatingPanel` 能做到；普通 `NSWindow` 设该 mask 通常无效（语义要求实例是 NSPanel）。而 P0 的"热键呼出面板 + ⌘1..9 直贴"整个建立在这上面。

三条出路（已写入文档，**待用户定**）：
- **A. v2 + cgo 换类**（推荐先试）：`NSApp.windows` → `object_setClass(win, [NSPanel class])` → 加 mask。~30 行，属未公开手法，跨 macOS 版本脆弱。
- **B. 上 Wails v3**：原生有 `MacWindowClassPanel` + `PanelPreferences{NonActivating: true}` —— 正是所需，但 v3 仍 alpha。
- **C. 接受抢焦点 + 事后补偿**：粘贴前 reactivate 前台 App 再发 ⌘V，多 100–150ms 且菜单栏闪动。

Windows 侧不受影响：`windows.Options.WindowClassName` → `FindWindow` → `SetWindowLongPtr(GWL_EXSTYLE, WS_EX_NOACTIVATE)`，无需 cgo。

**结论：M0 门禁未通过前不要写业务代码。**

### 采用方案（两个条件缺一不可）

1. **真正创建 NSPanel**（走正常 `alloc` / `initWithContentRect:`），再把 Wails 的 contentView 搬过来 —— **不能用 `object_setClass`**
2. **Accessory 激活策略**（`NSApplicationActivationPolicyAccessory`，或 `Info.plist` 的 `LSUIElement`）

外加一条顺序约束：**`orderFrontRegardless` 必须在 `makeKeyWindow` 之前**（窗口不可见时 `makeKeyWindow` 是空操作，顺序反了会得到"可见但收不到键盘"的面板）。

### 三条被实测否定的路（别再试）

| 路 | 现象 | 根因 |
|---|---|---|
| 给普通 NSWindow 加 `nonactivatingPanel` 位 | 系统打印 `NSWindow does not support nonactivating panel styleMask 0x80`，且 styleMask **实际未变**（32780 → 32780，bit7 仍 0） | mask 语义要求实例本身是 NSPanel |
| `object_setClass` 换类 | 换类"成功"（类名变了、能显示），随后任何 `orderOut` → **SIGTRAP** | Wails 窗口真实类是 `NSKVONotifying_WailsWindow`（KVO 动态子类，488 字节），带 `userMinSize`/`userMaxSize` 两个 NSSize ivar；NSPanel 布局与之重叠，调 `setFloatingPanel:` 等会写坏 Wails 的尺寸约束内存 |
| `makeKeyAndOrderFront:` 兜底 | 真激活了 App，0.7s 后被系统纠正、键盘焦点一并丢失 | 违反了 nonactivating 语义 |

### ⚠️ 认知修正：判据不是 `NSApp.isActive`

Accessory 策略下面板持有键盘焦点时 **`isActive` 是 true**，但 `NSWorkspace.frontmostApplication` 仍是原来那个 App —— **菜单栏没被抢走**。

初版 PoC 把 `active == false` 当通过条件，**因此把正确答案误判成 FAIL**。正确判据是"**frontmost 有没有被换成本 App**"。修正判据后同一份数据立刻 PASS。

### 实测数据（三次独立复现，结果一致）

| 指标 | 结果 |
|---|---|

### 遗留到 M2

2. **Wails 仍持有原窗口引用**，其 `SetSize`/`SetTitle` 会作用在已被掏空、隐藏的原窗口上 → 面板尺寸必须走自己的 NSPanel
