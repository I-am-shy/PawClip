## 两个自己找出来并修掉的真实缺陷（本轮最有价值的产出）

### 1. §12 检索延迟严重不达标（核心功能）

写了一条**规模化**验收测试 `store/latency_test.go`（10 万条，`-short` 下跳过），
一跑就红：

| 场景 | 旧的 `JOIN items_fts` 写法 | 修复后 |
|---|---|---|
| 稠密（命中 ~1 万） | p95 187～924 ms | **2～6 ms** |
| 稀疏（全库 1 条） | 0.4～2.7 ms | **0.36 / 0.45 ms** |
| 2 字 LIKE 兜底 | 0.53 ms | 0.45 / 0.76 ms |

（§12 预算：3 字以上 < 50 ms）

根因：`JOIN items_fts ON rowid = i.id` 让 SQLite **只能由 FTS 驱动**——把全部命中
回表、攒齐、再按 `created_at` 排序，**无法提前终止**，命中越多越慢且无上界。
改成 `i.id IN (SELECT rowid FROM items_fts WHERE items_fts MATCH ?)` 后计划里出现
`CREATE BLOOM FILTER`，可以按时间索引驱动、扫够一页就停。

**但只改这一处会换个方向翻车**：稀疏命中时按时间序扫要走完整张索引（实测 27～66 ms，
全量测试并行加载时真撞到过 66 ms 超标）。所以再按**命中密度自适应**：
`chooseFTSPlan` 用一条带上限的计数（`count(*) FROM (… LIMIT 2048)`）决定走
「物化排序」还是「时间索引扫描」。两条路的优劣完全相反，任何**固定**选择都会在另一
端留一个脆弱边界。

配套 `store/plan_test.go`：语义等价（与旧 JOIN 写法逐条比对 id 序列）+ 执行计划
（两个方向都断言）。**只测耗时不够**——库小的时候任何计划都是微秒级，恒绿。

### 2. 配置读不了时**静默退出**

`main.go` 原本 `LoadBootstrap` 失败就 `os.Exit(1)`。GUI 下 stderr 没人看得到 →
用户双击图标毫无反应。而同一项目里 `normalizeBootstrap` 的原则写的是"不让应用起不来"
——**值域**错了能继续跑、**语法**错了整个不启动，两处决定本来矛盾。
改为：用默认值启动 + `Health.BootWarning` 在界面显示常驻警告条（后端渲染、随语言）。

## 沉淀的可复用经验

- **BSD grep 不支持 `\|` 或中文**（macOS）：扫描中文/多模式一律用 ripgrep（Grep 工具），
  别用 `grep "a\|b"`，会静默返回空让你误判"没有命中"。
- **zsh 不对无引号变量做词分割**：`for t in "a b"; do set -- $t` 不会拆开，要显式写。
- **`INDEXED BY` 指定部分索引有前提**：`idx_items_alive` 是 `WHERE deleted_at IS NULL`
  的部分索引，回收站查询（`IS NOT NULL`）指定它直接报 `no query solution`，必须分支。
- **规模测试的"承重"要三件套**：走对了路径（`pg.Mode`）+ 真的命中了行（非空）+
  延迟在预算内。只断言耗时的话，把查询改成 `WHERE 0` 就能永远绿。
- **性能改写必须配语义等价测试**：把旧写法留在测试里作参照，等价性就不靠人肉 diff SQL。
- **i18n 的"够不着"层**：包级函数拿不到 `App.T()`，让它们传 `msgKey`、渲染推迟到进程
  边界，比在那里拼中文再想办法翻译干净得多。
- 反查"有没有漏"要用**测试**（`messages_test.go` 扫源码要求每个键有调用点、
  每句写死中文要么走 `msgf` 要么标 `// diag:`），靠"注意一下"守不住——本轮一次就查出 35 处。

## §12 补全：先量，再补

上一轮记的"空闲内存/CPU 没有真实数据"本轮解决了，但**不是靠 ps/top**——
受限环境（沙箱、部分 MDM）里 `ps`/`top` 属于"读别的进程"，会被直接拒绝
（实测 `operation not permitted: ps`，沙箱内外都拒）。改成**让进程自己报**：

- 新增 `resprobe.go`：启动后第 5s / 第 25s 各打一条 Debug 级「资源快照」，
  内容是常驻内存（`rss_darwin_cgo.go` 里已有的 Mach `task_info` 读自己）
  + 累计 CPU 时间（`cputime_unix.go` 的 `getrusage(RUSAGE_SELF)`）。
- **两次相减 = 这一段窗口的真实 CPU 占用率**，天然排除启动开销。
  `ps -o %cpu` 给的是"自启动以来均值"，会把启动摊进来、系统性偏高。
- 顺手在 `main.go` 的 `wails.Run` **之前**加了一条「启动基线」——这是把
  "WebKit 占了多少"和"Go/SQLite 占了多少"分开的唯一办法（建完窗口就再也分不开了）。

实测三点曲线：**基线 13 MB → 5s 59 MB → 25s 53 MB（稳态）**，
空闲 CPU **0.33–0.42%**（20 秒窗口）。结论：§12 那条「≤30 MB」超出的 41 MB
全在 Wails/WebKit 侧，Go+SQLite+捕获链路只占十几 MB；要达标只能不做/销毁
WebView，而 Wails v2.16 单窗口模型做不到。**如实标 ❌ 并写清归因**，不粉饰成 ✅。

新增 `capture/latency_test.go`（§12 第一行原先一条测试都没有）：
- 文本流水线 p95 **1.2 ms**（预算 30 ms）；5MB 图（1600×1200 噪声 PNG）端到端中位数 **108 ms**（预算 200 ms）。
- **造大图不能用 `makeSeededPNG`**：它的像素是 `(x*7+seed*31)%256` 线性图案，deflate 压得极小，
  2560×1920 也只有一两 MB。要用**真伪随机**像素（≈3 字节/像素），1600×1200 才到 5.8 MB。
- 图片用例断言**中位数**而不是最大值：实测预算是 200ms、空载 108ms 只有 1.8 倍余量，
  而 `go test ./...` 并行跑 10 个包时最大值能飙到 303ms（机器被占满，不是产品退化）。
  用最大值做判据 = 随机红 = 训练人忽略红色。CI 相应改成 `-p 1` 串行跑度量类用例。

## 本轮又抓到的真缺陷

1. **面板激活策略误报失败**（真机日志抓出来的，单测永远测不到）：
   `paw_set_accessory` 无脑调一次 `setActivationPolicy:Accessory` 再拿返回值判断。
   App 带 `LSUIElement=true` 启动时进程已经是 Accessory，这次调用返回 **NO（没变化，不是失败）**
   → 每次启动固定打一条 `WARN 切换到 Accessory 激活策略失败`。而这条 WARN 恰好出现在
   §0.2 认定的"免抢焦点必要条件"上，会把排查抢焦点的人带偏。
   修法：先读 `[NSApp activationPolicy]`，已是 Accessory 就直接返回成功并 log 一行。
2. **CI 的 `go build ./... -tags x` 写法是错的**：`go build` 把包后面的 `-tags`/`x`
   当**包路径**解析，报 `malformed import path "-tags"`。`go test` 对包后参数有兼容处理，
   所以同样写法在测试那一步能过——**这个不对称正是最容易抄错的地方**。改成 `go build -tags x ./...`。
   （这个仓库还没有 remote，CI 从未真跑过。）
3. **版本号有两份且不一致**：Info.plist 说 0.1.0（来自 wails.json），Go 侧 `main.Version`
   写死 `0.1.0-m1`，启动日志与关于窗口报的是后者。改成 `build.sh` 用 `-ldflags` 注入
   wails.json 的 productVersion（唯一真源），`release.yml` 用 tag 号覆盖；
   `release.yml` 同时改为**复用 build.sh**，不再自己重写一遍构建标签。
4. **验收脚本自己的 flake**：§12 去重那一项原先固定 `sleep 0.3` 复制 100 次，
   实测第一遍 100、第二遍 **99** —— 300ms 间隔撞上 200ms 轮询相位时，两次复制落进
   同一个轮询窗口、只被观测到一次。改成"每复制一次就等库里 `use_count` 涨到预期值再放下一次"，
   语义完整且确定。（这是**测量方式**的产物，不是去重语义的问题，但不能留在验收里当偶发红。）

## 沉淀的可复用经验（补）

- **受限环境里量进程资源，别用 ps/top**：用 `wait4` 的 rusage（父进程视角）或进程
  **自报**（Mach `task_info` 读自己 + `getrusage(RUSAGE_SELF)`）。后者还能做"窗口化"测量。
- **"窗口化"测 CPU 的办法**：取两次累计值相减 / 墙钟间隔。任何"自启动以来均值"的量
  （`ps -o %cpu`、top 第一次采样）都会把启动开销摊进来，不能用来判"空闲"。
- **要归因内存，必须在"建 UI 之前"打一个基线**：Wails 一建窗口，WebKit 就把 40MB 混进来，
  之后再也分不出是谁占的。
- **验收脚本里不要用固定 sleep 去对齐被测进程的轮询周期**：相位差会让它偶发差 1。
  要么等状态观测到，要么把判据放宽——别让它变成随机红。
- **验收脚本的失败项要保留**：把 §12 唯一不达标的项如实标 ❌ 并写清归因，
  比把它改成"仅提示"有价值得多——`accept.sh` 的退出码因此仍然有意义。
- **`zsh` 里中文引号嵌套会静默吃掉字符串**：`bad "…"面板销毁态"…"` 这种写法会拼接出错，
  中文文案里别再用 ASCII 双引号嵌套。

### 教训与可复用做法

- **移动文档 = 一次全局符号重命名，不是移动文件。** 这个仓库里代码注释引用设计条款
  **159 处 / 73 个文件**；只 `git mv` 的话这些指针全指空。改法是脚本批量替换：
  只替"点名了文档"的写法（`DESIGN.md`、`DESIGN §`），**不动裸 `§N`**——裸章节号靠上下文成立，
  硬加前缀反而更难读。用负向先行断言 `(?<!docs/)` 防二次加前缀。
- **文档一搬家，就会暴露原本就错的引用。** 这次揪出三处：`config.go` 生成到用户
  `config.toml` 里的「详见设计文档 §9.0」没法寻址；`DESIGN.md` §10 的目录树还停在设计期
  （没有 `scripts/*.sh`、没有 `.github/workflows/`、还有一个实际不存在的根 `package.json`）；
  同一节的构建命令表写的还是直接 `wails build`——正是本仓库最贵的那个坑。
- **写完使用者文档要逐条回代码核对。** 这次回查纠出两个会误导人的说法：
  ①「免抢焦点」只是 macOS 的能力（Win32 的 `WS_EX_NOACTIVATE` 窗口收不到键盘，
  所以 Windows 侧会取一次前台、粘贴后还回去）；②拼音示例的首字母写错了。
  文档里的"能力承诺"必须与平台实现一一对上。
- **验收脚本的段落编号会被文档引用**，所以改脚本顺序时要同步改引用（这次
  ③ 内存 / ⑥ 去重 / ⑦ 断电 就对不上过一次）。
- **数字要能被复算**：测试总数 257 条是 `go test -list '.*'` 逐包加的；"10 个包"其实只有
